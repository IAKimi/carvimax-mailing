¡Qué excelente iniciativa! El cambio de una cuenta centralizada a un modelo descentralizado (donde cada usuario conecta su propia API key) es el paso correcto para hacer que "PostIAlo Mailing" sea escalable, evitar problemas de reputación compartida y dar mayor control a tus usuarios.
A continuación, te detallo las respuestas técnicas y los ejemplos en Node.js usando fetch basados en la documentación oficial de la API de Brevo (v3).
1. ¿Qué tipo de cuenta necesitan tus usuarios?
Tus usuarios pueden utilizar cualquier tipo de cuenta de Brevo (Free, Starter, Standard, Professional o Enterprise)
. La API de Brevo está disponible en todos los planes. La única diferencia será el límite de envíos (cuota de la plataforma) que tengan contratado y los límites de tasa de peticiones (Rate limits) avanzados que se desbloquean en planes superiores
.
2. ¿Cómo obtienen y validan su API key?
Obtención: El usuario debe generar su API key directamente desde su cuenta de Brevo yendo al menú de su perfil y luego a Configuración SMTP y API (SMTP and API settings) > API Keys
. Al ser una API key directa, tiene los permisos necesarios para realizar los envíos
.
Validación (Llamada de prueba): Para verificar que la API key que ingresó el usuario es correcta sin enviar ningún correo, el endpoint ideal es GET /v3/account
. Este endpoint devuelve la información de la cuenta y valida si la API key es legítima
.
// Validación de la API Key en tu backend (Node.js)
async function validateBrevoApiKey(userApiKey) {
  try {
    const response = await fetch('https://api.brevo.com/v3/account', {
      method: 'GET',
      headers: {
        'accept': 'application/json',
        'api-key': userApiKey
      }
    });

    if (response.ok) {
      const data = await response.json();
      console.log('API Key válida. Cuenta de:', data.email);
      return true;
    } else {
      console.error('API Key inválida. Código de estado:', response.status);
      return false;
    }
  } catch (error) {
    console.error('Error en la validación:', error);
    return false;
  }
}
3. Endpoint para enviar correos
Para enviar emails transaccionales/masivos, usarás el endpoint POST /v3/smtp/email
.
URL: https://api.brevo.com/v3/smtp/email
Método: POST
Headers: accept: application/json, api-key: <API_KEY_DEL_USUARIO>, content-type: application/json
.
Si vas a iterar y enviar un correo individual por contacto, el cuerpo de la petición y el código serían así:
async function sendIndividualEmail(userApiKey, contact, senderData, subject, htmlContent) {
  const payload = {
    sender: {
      name: senderData.name,
      email: senderData.email
    },
    to: [
      {
        email: contact.email,
        name: contact.name
      }
    ],
    subject: subject,
    htmlContent: htmlContent
  };

  const response = await fetch('https://api.brevo.com/v3/smtp/email', {
    method: 'POST',
    headers: {
      'accept': 'application/json',
      'content-type': 'application/json',
      'api-key': userApiKey
    },
    body: JSON.stringify(payload)
  });

  return response.json(); // Retornará un 'messageId' en caso de éxito
}
💡 Recomendación de escalabilidad (Batch Send): Aunque mencionas que vas a iterar sobre la lista de contactos, Brevo permite enviar hasta 1,000 correos personalizados en una sola llamada a la API usando la estructura messageVersions
. Esto es mucho más eficiente que hacer un ciclo for que llame a la API cientos de veces y te ayudará a evitar problemas de latencia o bloqueos por rate limits.
4. ¿Hay límites de envío?
Existen dos tipos de límites que debes tener en cuenta
:
Rate limits de la API: La API en planes generales soporta hasta 1,000 peticiones por segundo (RPS) y 3,600,000 peticiones por hora (RPH) en el endpoint POST /v3/smtp/email
. Si excedes esto, recibirás un error 429 Too Many Requests
.
Cuotas de la Plataforma: El volumen máximo de correos que el usuario puede enviar al mes o al día dependerá exclusivamente del plan de Brevo que él pague (por ejemplo, el plan Free tiene un límite de 300 emails por día)
.
5. ¿El email del remitente (sender) necesita estar verificado?
Sí. Para que Brevo permita hacer envíos, el dominio y la dirección del remitente deben estar autenticados y verificados en la cuenta del usuario
.
¿Cómo verificarlo programáticamente? Puedes consultar la lista de remitentes aprobados en la cuenta del usuario utilizando el endpoint GET /v3/senders
. Si el email del remitente existe en esa lista, significa que está configurado y activo en su cuenta.
async function checkSenderExists(userApiKey, senderEmail) {
  const response = await fetch('https://api.brevo.com/v3/senders', {
    method: 'GET',
    headers: {
      'accept': 'application/json',
      'api-key': userApiKey
    }
  });
  
  if (response.ok) {
    const data = await response.json();
    // Verificar si el email que quiere usar está en la lista de senders de su cuenta
    const isVerified = data.senders.some(sender => sender.email === senderEmail);
    return isVerified;
  }
  return false;
}
6. Seguimiento del estado del email (Entregado, Abierto, Rebotado)
Para actualizar tu campaña en tiempo real en tu frontend, la práctica recomendada (y más escalable) por la API de Brevo no es hacer un polling consultando endpoint por endpoint, sino utilizar Webhooks Transaccionales
.
Brevo enviará un POST (JSON) automático a tu backend (por ejemplo, a un endpoint tuyo POST /api/webhooks/brevo) cuando ocurran los siguientes eventos: Sent, Delivered, Opened, Clicked, Soft Bounce, Hard Bounce, etc.
.
Tu usuario puede configurar este webhook en su dashboard de Brevo, o tú puedes crearlo programáticamente usando su API key mediante el endpoint POST /v3/webhooks
.
El payload que recibirás en tu backend de Node.js cuando un email se entregue será similar a este:
{
  "event": "delivered",
  "email": "example@example.com",
  "id": 26224,
  "message-id": "<xxxxxx@domain.com>",
  "subject": "Asunto de la campaña",
  "tags": ["postialo_campaign_123"]
}
Nota: Puedes enviar un parámetro tags en tu payload de envío original (ej. tu campaign_id interno) para que cuando Brevo te envíe el webhook, sepas exactamente a qué campaña de tu base de datos corresponde ese evento
.
